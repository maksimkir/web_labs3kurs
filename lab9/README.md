# Study Planner — лабораторна робота №9

**Тема:** React State та Effects: Context API, useReducer, useEffect і Custom Hooks.

Продовження Study Planner з лабораторної №8. Функціонал №8 (створення, виконання, фільтр, пошук,
сортування, статистика, порожні стани) збережено, але стан перебудовано:

- `tasks` керує **useReducer** з типізованими діями;
- спільний стан і дії доступні через **Context API** (`TaskContext`, `TaskProvider`, `useTaskContext`);
- завдання й активний фільтр зберігаються в **localStorage** між перезавантаженнями;
- **редагування** завдання, власні **Toast**-повідомлення та **Undoable Delete** з 5-секундним таймером;
- заголовок вкладки показує кількість невиконаних завдань.

Стек: React 19 + TypeScript, Vite, SCSS + BEM, ESLint.

## Як влаштовано

**Reducer.** `taskReducer(state, action)` — чиста функція без HTTP, DOM, localStorage і таймерів.
Дії: `add`, `toggle`, `update`, `requestDelete`, `confirmDelete`, `undoDelete`, `clearCompleted`
(з тим самим undo-flow), `reset`, `sync` (зміни з іншої вкладки). Кожна дія — окремий TypeScript-тип
з власним payload (`TaskAction`).

**Context.** `TaskProvider` створює стан і дії, `useMemo` / `useCallback` не дають створювати новий
об'єкт `value` без потреби. Компоненти (`TaskList`, `TaskItem`, `TaskFilters`, `TaskStats`,
`TaskToolbar`, `ToastContainer`) беруть потрібне через `useTaskContext()` — без prop drilling.

**Persistence.** Reducer ініціалізується ліниво з `localStorage` (`useReducer(taskReducer, undefined, initState)`);
пошкоджені чи відсутні дані → початковий список. Після кожної зміни `tasks` `useEffect` записує їх у
сховище. Фільтр і тема зберігаються через `useLocalStorage<T>()`. `tasks` лишаються єдиним джерелом
правди — localStorage лише зберігає їх між сесіями.

**Effects.**

| Effect | Що синхронізує |
|---|---|
| збереження `tasks` | React state → localStorage |
| таймер Undoable Delete | запуск `setTimeout` на 5 с, `clearTimeout` у cleanup |
| `document.title` | кількість невиконаних завдань → заголовок вкладки |
| подія `storage` | зміни з іншої вкладки → `dispatch({ type: 'sync' })` |
| автозакриття Toast | `setTimeout` на 3 с у кожному повідомленні |

Відфільтрований список і статистика — derived state: обчислюються під час рендеру (`useMemo`), не в ефектах.

**Undoable Delete.** «Видалити» → `requestDelete` позначає завдання (`pendingDelete`), картка
приглушується з написом «Буде видалено», з'являється toast з прогресом і кнопкою «Скасувати».
Ефект запускає таймер на 5 с: по завершенні — `confirmDelete` і toast «Видалено». «Скасувати» →
`undoDelete`, cleanup ефекту очищує таймер. Одночасно активне одне видалення: нове завершує попереднє.
Незавершене видалення після перезавантаження не відновлюється.

**useEffectEvent.** Колбек таймера (`onUndoTimeout`) оголошено через `useEffectEvent`: він читає
актуальні `pendingDelete` і `toast`, але не є залежністю ефекту. Звичайний ефект мав би в залежностях
`toast` і `pendingDelete`, і будь-яка їх зміна перезапускала б 5-секундний таймер.

## Додаткові завдання

- синхронізація між вкладками через подію `storage`;
- окремий `ThemeContext` зі збереженням теми;
- масове видалення виконаних з можливістю Undo;
- оптимізація `value` контексту (`useMemo`, `useCallback`);
- `useEffectEvent` для колбека таймера.

## Відповіді на контрольні запитання

**1. Коли state доцільно піднімати у батьківський компонент?**
Коли ті самі дані потрібні кільком компонентам або один компонент має змінювати дані іншого.
Стан переносять у найближчого спільного батька, а дітям передають значення і callback-и.

**2. Що таке prop drilling і яку проблему вирішує Context API?**
Передача props через кілька проміжних компонентів, яким ці дані самим не потрібні (`App → TaskList →
TaskItem → кнопка`). Context дає будь-якому нащадку прочитати значення напряму через `useContext`.

**3. Що таке reducer? Чим він відрізняється від звичайної функції оновлення state?**
Функція `(state, action) => newState`, яка в одному місці описує всі способи змінити стан. На відміну
від розкиданих `setState`, логіка зібрана разом, а компоненти лише повідомляють, що сталося (`dispatch`).

**4. Якою повинна бути чиста reducer-функція?**
Однаковий вхід → однаковий результат; без побічних ефектів (HTTP, DOM, localStorage, таймери);
не змінює вхідний state, а повертає новий об'єкт.

**5. Що таке action і dispatch?**
Action — об'єкт, що описує подію: `{ type: 'toggle', id: 3 }`. `dispatch(action)` передає його в
reducer, React обчислює новий стан і перерендерює компонент.

**6. Коли `useReducer` доцільніше за `useState`?**
Коли стан складний або має багато пов'язаних змін (додати, змінити, видалити, скасувати), коли новий
стан залежить від попереднього й кількох полів одночасно, або коли логіку зручно тестувати окремо.

**7. Що таке Context API і з яких частин складається його використання?**
Механізм передачі даних деревом компонентів без props. Частини: `createContext()` — створення,
провайдер `<TaskContext value={...}>` — надання значення, `useContext()` (тут `useTaskContext()`) — читання.

**8. Чи потрібно через Context передавати весь state застосунку?**
Ні. Лише те, що справді потрібно багатьом компонентам. Локальний UI-стан (наприклад, режим редагування
картки) лишається в компоненті; незалежні речі краще в окремих контекстах (тут — `ThemeContext`),
щоб зміна однієї не перерендерювала всіх.

**9. Що таке side effect у React?**
Дія, що виходить за межі обчислення JSX: запис у localStorage, таймер, зміна `document.title`,
підписка на подію, HTTP-запит.

**10. Для чого використовується `useEffect`?**
Для синхронізації компонента із зовнішніми системами після рендеру: сховищем, таймерами, API браузера,
підписками.

**11. Коли запускається Effect і коли виконується cleanup?**
Effect — після рендеру, коли компонент з'явився і щоразу, коли змінилися залежності. Cleanup — перед
наступним запуском ефекту (зі старими значеннями) і при видаленні компонента.

**12. Чому запис у `localStorage` є побічним ефектом?**
Він змінює зовнішнє сховище браузера, а не повертає JSX. Рендер має бути чистим, тому запис робиться
в `useEffect` після зміни `tasks`.

**13. Чому timer для Undoable Delete не можна створювати всередині reducer?**
Reducer має бути чистим: React може викликати його повторно (StrictMode), і таймер створився б двічі.
Reducer лише змінює стан (`pendingDelete`), а таймер запускає ефект.

**14. Для чого потрібен `clearTimeout` у cleanup?**
Щоб старий таймер не спрацював після скасування, нового видалення чи unmount: інакше видалилося б не
те завдання або оновився б стан демонтованого компонента.

**15. Чому не варто дублювати derived state?**
Дані, які можна обчислити з наявного стану (відфільтрований список, статистика), у окремому state
можуть розсинхронізуватися й потребують зайвих оновлень. Їх обчислюють під час рендеру.

**16. Що таке Custom Hook?**
Функція з назвою на `use`, яка використовує інші хуки й повторно використовує логіку стану або ефектів:
`useTaskContext`, `useLocalStorage`, `useToasts`, `useTheme`.

**17. Які правила потрібно дотримуватися при створенні власних hooks?**
Назва починається з `use`; хуки викликаються лише на верхньому рівні (не в умовах і циклах) і лише з
компонентів або інших хуків; кожен виклик має власний незалежний стан; хук повертає значення/функції,
а не JSX.
